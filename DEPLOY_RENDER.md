# GradeFlow on Render

The repository includes a Docker web service and Render Blueprint with a PostgreSQL database named `gradeflow-db`. The XAMPP database on your computer cannot be used by the deployed app.

1. Push this project to a **private** Git repository. Keep `.env`, database dumps, and student records out of the repository.
2. Use the PostgreSQL database created by the Blueprint. For an existing manually created web service, create a Render PostgreSQL database in the same region and copy its Internal Database URL into the service's `DB_URL` environment variable. Set `DB_CONNECTION=pgsql`.
3. In Render, create a **Blueprint** from the repository. Render reads `render.yaml` and builds the Docker image.
4. Set the Blueprint secrets when prompted:
   - `APP_KEY`: generate locally with `php artisan key:generate --show`.
   - `DB_URL`: supplied automatically by the Blueprint from `gradeflow-db`. For a manually created service, set this to the Render PostgreSQL Internal Database URL, **not** `127.0.0.1` or XAMPP.
   - `ADMIN_EMAIL`: email for the first administrator.
   - `ADMIN_PASSWORD`: a unique password of at least 12 characters.
5. Deploy and open the assigned `https://...onrender.com/admin/login` URL. The first start runs migrations and creates the first administrator only if none exists. Later starts do not overwrite that account.

The Blueprint uses a free web-service plan for a group demo. Free services can sleep, and the separate database may have its own costs or limits. Do not use a short-lived or unbacked database for real student records. The app is configured with `APP_DEBUG=false`, database sessions and cache, and HTTPS URLs. Do not run `DemoDataSeeder` on a live student system.

Startup seeds the seven subjects from the local subject catalog using `SubjectSeeder`: 26-01, ITE101, ITE102, ITE315, ELEC3, GE311, and ITE311. Each new subject has 3.0 units and active status. Existing subject codes are skipped, preserving edits and preventing duplicates on redeployment. IDs and timestamps are generated by the online database. No students, grades, or demonstration accounts are imported.

Push these changes to the repository branch connected to Render and redeploy the web service to populate its database. To populate an already running service immediately from its Render Shell, run `php artisan db:seed --class=SubjectSeeder --force`. Do not upload a copy of the local XAMPP database without checking privacy and removing demonstration accounts first. If you change the Dockerfile or `render.yaml`, redeploy from Render.

For an existing service, repository changes to `render.yaml` apply through a linked Blueprint; they do not automatically configure a manually created service. Check that the service uses the Docker runtime and that its Docker Command is blank (uses the image default) or `/usr/local/bin/gradeflow-start`.

If a deployment fails, check its build and runtime logs. `Set APP_KEY` or `Set DB_URL` means the corresponding environment variable is missing. A database connection error during `migrate --force` requires checking the database status and connection URL. `Set ADMIN_EMAIL and a unique ADMIN_PASSWORD` requires valid initial administrator credentials, including a password of at least 12 characters. Startup intentionally stops on these errors, so Apache cannot pass the `/up` health check until they are resolved.

If PostgreSQL reports `could not translate host name` for a host beginning with `dpg-` and ending with `-a`, the service is using a Render internal database URL outside the private network where that URL is valid. Confirm that the web service and database are active, belong to the same Render workspace, and use the same region. Then copy the database's current Internal Database URL into `DB_URL`. If they cannot share a region, use the database's External Database URL instead and keep it secret.
